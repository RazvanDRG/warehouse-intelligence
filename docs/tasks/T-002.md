# T-002: Read System 1 events from Kafka through a generic EventSource

Status: in review · Branch: task/T-002-event-source · Risk: high (System 1 event contract, critical file adapters/warehouse/events*.py, new dependency)

## What we're building
The AI system can read System 1's events from Kafka through one interface. The core sees plain events (id, type, time, entity, payload) and never knows they came from Kafka.

## Done when
Each point is something you can see working, and the test that proves it.
- AC-1: `core/events.py` defines `Event` (event_id, type, occurred_at, entity, payload) and an `EventSource` Protocol with `consume(handler)`; core holds no warehouse terms. (tests: `tests/test_events.py::test_kafka_source_is_an_event_source`, `tests/test_layout.py::test_core_does_not_import_adapters`)
- AC-2: `adapters/warehouse/events.py` turns a message in the docs/architecture.md section 4 envelope (event_id, event_type, occurred_at, order_id, request_id, payload) into an `Event`; a missing field or broken JSON raises a clear parse error, which stops the consumer with no commit. (tests: `test_parse_valid_envelope`, `test_parse_missing_field`, `test_parse_broken_json`, `test_no_commit_on_parse_error`)
- AC-3: the offset is committed only after the handler finishes; a failing handler means no commit. (tests: `test_commit_after_handler`, `test_no_commit_when_handler_fails`, fake consumer, no real Kafka)
- AC-4: consumer settings come from `KAFKA_*` environment variables: own group id, auto-commit off, the 4 section 4 topics, SASL_SSL with username, password and CA file for Aiven; PLAINTEXT allowed for local runs. (tests: `test_consumer_config_sasl_ssl`, `test_consumer_config_plaintext`)
- AC-5: `.env.example` lists the new `KAFKA_*` names with no values. (test: `test_env_example_lists_kafka_names`)
