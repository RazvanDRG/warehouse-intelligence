# T-004 (d3.w2): dead-letter for the event consumer, Week 2 Wed

Status: agreed · Branch: task/T-004-d3w2-dead-letter · Risk: high (new table and migration, changes to the consumer loop and the critical System 1 envelope parser)

## What we're building
Today one bad message stops the consumer for good: it never commits, so every restart reads the same bad message again. After this task, a message that cannot be read (broken JSON, wrong fields, empty tombstone) is saved to a dead_letters table with its error and the consumer moves on; a handler that fails is retried, and if it still fails its message is dead-lettered too. A database outage stops the consumer instead, so events are not dead-lettered by mistake.

- AC-4: the handler fails once then succeeds: it is retried, nothing is dead-lettered, the event is saved once. (test: `tests/test_deadletter.py`)
- AC-5: the handler fails on all 3 tries: one dead_letters row with the last error, no processed_events row, offset committed, the consumer continues with the next message. (test: `tests/test_deadletter.py`)
- AC-6: a database connection error in the handler, or a failed dead_letters write: the consumer stops, commits no offset and writes no dead letter. (test: `tests/test_events.py`)

## Open questions
Answered before any code is written.
- Columns? (answer: architecture columns plus partition and offset; payload as raw bytes, NULL for a tombstone. D-018)
- Handler keeps failing? (answer: 3 tries with waits of 0.5s then 1s, then dead-letter, commit, continue. D-019)
- Database down? (answer: connection errors stop the consumer without committing; never dead-lettered. D-020)
- Same broken message delivered twice? (answer: unique rule on (topic, partition, offset); the existing row is kept. D-022)
- Wiring? (answer: a generic DeadLetterSink in core/deadletter.py, passed to KafkaEventSource; EventSource.consume(handler) unchanged. D-021)
